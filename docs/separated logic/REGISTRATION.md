# Registration specification

Baseline: 2026-10-02. Language: English. This standalone specification covers registration only: UI behavior, API contract, validation, persistence and acceptance scenarios. CSRF acquisition is included as a prerequisite. Other account and workspace operations are outside its scope.

## 1. Entry points

| Purpose | Request |
| --- | --- |
| Open the form | `GET /register/` |
| Submit through the JSON API | `POST /api/auth/register/` |
| Submit without JavaScript | `POST /register/` (form-encoded) |
| Obtain a CSRF token | `GET /api/auth/csrf/` |

The browser uses the JSON API when JavaScript is enabled and ordinary form submission otherwise. All URLs include a trailing slash.

## 2. Registration requirements

### 2.1 Form

The page displays **Create an account**, the subtitle **Your private task workspace.**, a **Create account** submit button, a Back link to `/`, and a **Log in** link to `/login/`.

| Field | API name / test ID | Required | Rules |
| --- | --- | --- | --- |
| Username | `username` | Yes | Maximum 150 characters. Django username validation permits Unicode letters/digits and `@`, `.`, `+`, `-`, `_`. Surrounding whitespace is trimmed; Django's username field applies Unicode normalization. Existing usernames are rejected by the registration form. |
| Email | `email` | Yes | Must pass Django email validation and User model validation. Surrounding whitespace is trimmed. An email address may be reused by another account. |
| Password | `password1` | Yes | At least 8 characters; must pass all configured password validators. Password whitespace is not trimmed. |
| Password confirmation | `password2` | Yes | Must exactly match the password, including case and whitespace. |
| Terms checkbox | `terms` | Yes | Label: `I accept the training workspace terms`. Must be checked; JSON API requires boolean `true`. |

Configured password validators reject passwords that are too similar to user attributes, shorter than 8 characters, commonly used, or entirely numeric. There is no custom rule requiring a particular combination of uppercase, lowercase, digits and symbols. The same password rules do not run again during login: login verifies the existing password.

### 2.2 Behavior

| ID | Requirement |
| --- | --- |
| REG-01 | An anonymous visitor can open the registration form without an existing session. |
| REG-02 | Valid input creates one user account and immediately authenticates that user. No separate login or email-confirmation step is required. |
| REG-03 | Success navigates to `/tasks/` and displays `Account created. Welcome!`. Registration has no supported `next` field or alternate destination. |
| REG-04 | Missing fields, malformed email, invalid username, rejected password, mismatched confirmation or unaccepted terms prevent account creation and display validation errors. |
| REG-05 | An existing username produces a username validation error. The ordinary API response is 400. A competing registration that creates the username between validation and save produces 409 with a validation error. |
| REG-06 | An authenticated visitor opening `/register/` is redirected to `/tasks/`. A validly formed API registration request from an authenticated session returns 409 `already_authenticated`. |
| REG-07 | Registration does not create demo data. Password values are never returned in API responses. |

### 2.3 API request and success response

```http
POST /api/auth/register/
Content-Type: application/json
X-CSRFToken: <token>
Cookie: <cookies retained from the CSRF request>
```

```json
{
  "username": "qa_student",
  "email": "student@example.com",
  "password1": "TrainingPassword_8642!",
  "password2": "TrainingPassword_8642!",
  "terms": true
}
```

Success: **201 Created**. Example ID and token below are placeholders for values generated by the server.

```json
{
  "user": {
    "id": 42,
    "username": "qa_student",
    "email": "student@example.com"
  },
  "csrfToken": "<new-token>",
  "redirect_url": "/tasks/",
  "message": "Account created. Welcome!"
}
```

The API returns JSON rather than an HTTP redirect. The browser navigates using `redirect_url`. The `user` object contains only ID, username and email.

## 3. CSRF and request validation

Before the POST, request `GET /api/auth/csrf/`. It is public and returns **200 OK** with `{"csrfToken":"<token>"}` and the CSRF cookie. Retain response cookies and send the token as `X-CSRFToken`. A session is not required before registration, but CSRF validation is required.

After successful registration, Django rotates the CSRF token; use the new `csrfToken` and updated cookies in subsequent requests. The JavaScript client fetches a token before its first write and updates its cached token from successful authentication responses. On a CSRF failure it clears the cache, displays the error, and fetches a fresh token on the next attempt; it does not automatically replay the failed request.

Validation order is significant:

1. Django middleware checks CSRF for unsafe requests.
2. The endpoint checks the HTTP method.
3. POST requires `Content-Type: application/json`, valid JSON and a top-level object.
4. Unknown fields and incorrect JSON types are rejected.
5. Registration checks whether the requester is already authenticated; then the registration form validates input and performs the operation.

Allowed registration keys are exactly `username`, `email`, `password1`, `password2`, `terms`. All supplied values must be strings except `terms`, which must be a JSON boolean. Null, numeric or array values are not valid substitutes. Unknown keys such as `id`, `is_staff` or `remember_me` are rejected. An empty object is valid JSON but fails required-field validation.

### 3.1 Errors

Errors use the following envelope. `fields` is included for validation errors; each field maps to an array of messages. General form errors use `__all__`.

```json
{
  "error": {
    "code": "validation_error",
    "message": "Please correct the highlighted fields.",
    "fields": {
      "username": ["This field is required."]
    }
  }
}
```

| HTTP status | Code | Condition / message |
| --- | --- | --- |
| 400 | `invalid_json` | Malformed/empty JSON: `The request body must be valid JSON.` Non-object JSON: `The request body must be a JSON object.` |
| 400 | `validation_error` | Wrong types/unknown fields: `Invalid fields.` Form errors: `Please correct the highlighted fields.` |
| 403 | `csrf_failed` | `Refresh the CSRF token and try again.` |
| 405 | `method_not_allowed` | `Method not allowed.` with `Allow: POST` for registration, or `Allow: GET` for CSRF acquisition. |
| 409 | `already_authenticated` | API registration while authenticated: `Log out before creating another account.` |
| 409 | `validation_error` | Concurrent username creation detected when saving registration. |
| 415 | `unsupported_media_type` | `Use Content-Type: application/json.` |

Missing CSRF can mask payload or method errors with 403. API paths without the required trailing slash reach the API catch-all and return JSON 404. Exact framework validation messages follow the installed Django version; tests should assert stable status, code and field keys where exact wording is not necessary.

## 4. Form interaction and HTML fallback

| ID | Requirement |
| --- | --- |
| REGISTRATION-FORM-01 | The form uses `novalidate`, so server validation handles errors instead of native browser validation popups. Password inputs mask their values. |
| REGISTRATION-FORM-02 | JavaScript submission clears previous errors, disables the submit button, changes its text to `Please wait…`, and marks the form `aria-busy="true"`. Further submissions while busy are ignored. |
| REGISTRATION-FORM-03 | API errors display an alert summary. Matching field errors mark inputs with `aria-invalid` and `aria-errormessage`; the first matched invalid field receives focus. General errors appear in the summary. |
| REGISTRATION-FORM-04 | A failed JavaScript request leaves the user on the form with entered values available for correction. The button and busy state are restored after the request. |
| REGISTRATION-FORM-05 | Successful JavaScript submission stores a one-time notification in session storage before navigating. If storage is unavailable, authentication and navigation still work, but the notification may be absent. |
| REGISTRATION-FORM-06 | Without JavaScript, registration POSTs use form-encoded input and the hidden CSRF form token. Invalid submissions re-render the form with errors and HTTP 200; password fields are not repopulated by Django. |
| REGISTRATION-FORM-07 | Successful HTML registration redirects to `/tasks/` with HTTP 302 and a Django success message. |

Automation hooks: `register-form`, each field's API name, `submit`, `form-errors`, `error-{field}`, and `notification`. Scope field and submit locators to the relevant form. The authenticated header exposes `current-user` for checking the resulting username.

## 5. Persistence checks

Registration creates a Django `auth_user` row with a generated ID, validated username/email and a hashed password. It does not store the raw password, confirmation or terms checkbox as separate columns. Ordinary registration does not grant staff or superuser privileges. Session persistence uses Django's configured session backend.

Verify that successful registration adds exactly one user and that the stored password passes Django's password-checking API. Failed registration must not add a user. The new authenticated session should remain effective after navigating or refreshing. No email verification, multifactor enrollment or social-registration flow is implemented.

## 6. Acceptance scenarios

Use isolated users and valid CSRF cookies/tokens unless CSRF failure is the intended test. Each row describes a separate scenario or a parameterized set of cases.

| ID | Scenario | Expected result |
| --- | --- | --- |
| REG-T01 | Submit valid unique registration with accepted terms. | 201; one new user; authenticated session; new CSRF token; navigation and welcome notice. |
| REG-T02 | Omit each required field or submit an empty required string; omit terms or set it to false. | 400 validation error for the affected field; no user created. |
| REG-T03 | Submit invalid username characters or a username longer than 150 characters. | Username validation error; no account created. |
| REG-T04 | Submit a valid 150-character unique username with otherwise acceptable data. | Registration accepted. |
| REG-T05 | Submit malformed email; separately reuse a valid existing account's email with a new username. | Malformed email rejected; email reuse allowed. |
| REG-T06 | Submit passwords of 7 and 8 characters, chosen to satisfy every other validator. | 7 rejected for length; 8 accepted if all other rules pass. |
| REG-T07 | Submit common, numeric-only or user-similar passwords; separately mismatch confirmation. | Password/confirmation validation errors; no user created. |
| REG-T08 | Register an existing username; separately simulate a save-time competing creation. | Ordinary duplicate: 400; handled save-time conflict: 409; no second user. |
| REG-T09 | Open the registration page while authenticated; separately submit a valid API request. | Page redirects to `/tasks/`; API returns 409 `already_authenticated`. |
| REGISTRATION-API-T01 | Submit malformed JSON, a JSON array, incorrect field types, and unknown body keys. | 400 with appropriate code/field errors. |
| REGISTRATION-API-T02 | Submit without JSON content type; separately omit/alter CSRF token. | Valid-CSRF media-type failure: 415; CSRF failure: 403. |
| REGISTRATION-API-T03 | GET the registration API endpoint. | 405 with `Allow: POST`. |
| REGISTRATION-API-T04 | Submit twice while the first browser request is pending. | One in-flight form operation; disabled button and busy state visible. |
| REGISTRATION-API-T05 | Correct a failed submission and retry. | Previous errors clear; corrected data is accepted; user reaches the success destination. |
| REGISTRATION-API-T06 | Disable JavaScript and repeat valid and invalid form submissions. | HTML response/redirect behavior matches section 4. |
